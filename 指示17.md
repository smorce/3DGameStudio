# 3DGameStudio ワールド生成基盤 + Asset Factory 実装指示

あなたは、このリポジトリを実際に変更するシニアゲームエンジン／TypeScriptエンジニアです。

対象:

Repository:
https://github.com/smorce/3DGameStudio

ベースブランチ:
perf/async-world-streaming-frame-budget

このブランチを必ず基準にしてください。

新しい作業ブランチを作って実装してください。
例:

feat/world-generation-asset-factory

既存の非同期ワールドストリーミング基盤、Worker、フレーム時間予算、Floating Origin、Terrain Edit、既存World、既存Asset Pipelineを壊さないでください。


==================================================
0. 今回の目的
==================================================

3DGameStudioに、

「人間が大きな世界構造を設計し、
細部を決定的に手続き生成し、
必要なアセットをAsset Factoryで集め、
Asset Processorを通し、
Asset Catalogから利用する」

というワールド制作基盤を実装してください。

最終的な責務は以下です。

World Design
    ↓
Semantic Layers
    ↓
Terrain / Road / Biome / Prop / Landmark Generation
    ↓
Asset Slot
    ↓
Asset Resolver
    ↓
Asset Catalog

Assetが不足する場合のみ開発時に:

Asset Requirement Planner
    ↓
Asset Factory
    ↓
External Providers / Dummy Astra
    ↓
Asset Processor
    ↓
Asset Catalog

RuntimeからAsset Factoryや外部サービスを呼んではいけません。


==================================================
1. 今回確定している設計
==================================================

以下は変更しないでください。

1. World Designは保存する。

2. Terrainはチャンク単位で決定的に生成する。

3. 木、岩、草、小物などは、
   モデル自体はAsset Library / Catalogに保存し、
   配置だけを実行時に決定的生成する。

4. 町、空港、灯台、橋、ジャンプ台など、
   ワールドの意味を持つ重要物はWorld Designに固定配置する。

5. World DesignとTerrain Generatorの間に
   Semantic Layersを設ける。

6. Generatorは特定のGLBやproviderを直接参照せず、
   Asset Slotを出力する。

例:

nature.tree.tropical.medium

nature.rock.small

building.village.house

landmark.lighthouse

course.jump_ramp

7. Asset ResolverがAsset SlotからAssetを選ぶ。

8. Asset Catalogは、
   Assetを「取得・生成・加工」しない。

Catalogの責務は、

- 登録
- インデックス
- 検索
- Slot解決
- Metadata管理

のみ。

9. Asset FactoryはAssetを用意する。

10. Asset Factory → Asset Processor → Asset Catalog
    の順序を厳守する。

11. Asset Requirement Plannerは今回はDUMMY実装。

12. AstraによるAsset生成も今回はDUMMY実装。

外部のOpenAI API、
GPT-6 Astra、
Blender自動操作サービス等へ
実際の課金リクエストを送ってはいけない。

13. RuntimeではネットワークAsset検索・生成を絶対に行わない。

14. パネキットのコピーは作らない。

既存ゲーム固有の

- マップ
- モデル
- テクスチャ
- キャラクター
- 固有ランドマーク

をコピーしない。

目標は

「自作マシンで陸・海・空を自由に移動できる、
明るい低ポリゴンの独自群島ワールド」

である。

WorldDesign

- version
- islands
- roads
- settlements
- airports
- landmarks
- biomeRegions
- noSpawnRegions
- gameplayRegions


IslandDefinition

- id
- center
- radius / shape
- baseHeight
- coastWidth
- biome
- mountains
- propRules


MountainDefinition

- center
- radius
- height
- falloff


RoadDefinition

- id
- controlPoints
- width
- shoulderWidth
- terrainFalloff
- elevationMode


LandmarkDefinition

- id
- assetSlot

==================================================
6. Semantic Layers
==================================================

World Designから巨大なRasterデータを保存するのではなく、

world coordinate

(x, z)

に対して問い合わせ可能な
決定的なsampling APIを基本にしてください。

例:

sampleIslandMask(x, z)
sampleHeightMask(x, z)
sampleCoastMask(x, z)
sampleBiome(x, z)
sampleRoadInfluence(x, z)
sampleSettlementMask(x, z)
sampleNoSpawnMask(x, z)

必要ならChunk単位のcacheを作ってよいです。

Semantic Layerは、

Terrain Generator
Prop Generator
Validator

が共有してください。

各Generatorが独自に
道路位置や島位置を再計算する設計は禁止です。


==================================================
7. Seed Namespace
==================================================

現在の

seed + 9
seed + 13
seed + 99

のような暗黙的Seed派生を整理してください。

以下のようなAPIを作ってください。

deriveSeed(
  worldSeed,
  namespace,
  optionalStableId
)

namespace例:

terrain
macro-terrain
coast
mountain
biome
road
tree
rock
grass
prop
asset-variant
landmark

同じ入力なら必ず同じ値を返すこと。

Generatorの一部を変更しても、
無関係なGeneratorの乱数列まで変わりにくい構成にしてください。


==================================================
8. Terrain Generation
==================================================

terrainは

「Noiseが世界を決める」

のではなく、

「World Designが世界を決め、
Noiseが自然な細部を追加する」

構成にしてください。


基本:

finalHeight =
    macroTerrain
  + mountainInfluence
  + coastInfluence
  + weakFBMDetail
  + roadConform


島の

- 位置
- 大きさ
- 山の位置
- 道路
- 空港
- 町

はNoise任せにしないこと。


==================================================
9. Macro / Meso / Micro
==================================================

生成概念を3階層に分けてください。

MACRO

- 島
- 山
- 海
- 大規模ランドマーク

MESO

- 道路
- 森
- 集落
- 岩場
- 海岸

MICRO

- 木
- 草
- 小石
- 小物


現在の32m Chunk Streamingは維持してください。

この階層のために
Runtime Streamingを全面的に作り直してはいけません。

まずWorld Generator内部で
異なる空間スケールを扱える構造を作ってください。


==================================================
10. Road Terrain Conform
==================================================

道路を完成済み地形の上へ置くだけにしないでください。

Road Definitionから道路の影響範囲を計算し、

道路中心
道路幅
shoulder
falloff

を使って地形を道路へ滑らかに寄せてください。

最低条件:

- 道路中央が不自然に地面へ埋まらない
- 空中へ浮かない
- 道路横が突然崖にならない
- Chunk境界で段差が生じない

道路経路はSplineとして表現できるSchemaにしてください。

最初の実装は、
決定的で十分に滑らかな
Catmull-Rom等の評価器でよいです。


==================================================
11. Prop Generator
==================================================

GeneratedEntityを

rock/tree/building

という固定enumだけで扱う構造から発展させてください。

Generatorが主に出力するのは

assetSlot

です。

例:

{
  id,
  assetSlot: "nature.tree.tropical.medium",
  position,
  rotation,
  scale
}


必要なら互換用kindを残して構いません。

ただし新しいGeneratorは
特定Asset IDやGLBファイルを直接指定しないこと。


==================================================
12. Prop Placement Rules
==================================================

単純なchunk内乱数配置から発展させてください。

配置条件:

- biome
- altitude
- slope
- water distance
- road distance
- landmark distance
- no-spawn
- minimum spacing

を評価してください。

木が

- 道路上
- 滑走路上
- 海中
- 急斜面
- 建物入口

などへ出ないようにしてください。


==================================================
13. Chunk境界に強い配置
==================================================

Chunkごとに独立した単純乱数を使った結果、

Chunk境界だけ密度が変わる
木同士が重なる

という状態を避けてください。

完全なBridson Poisson Diskでなくても構いません。

推奨:

world-space deterministic cell
+
jitter
+
neighbour rejection

によるBlue Noiseに近い配置。

Chunkをまたぐ判定ではhalo領域を評価してください。

同じSeedならChunkの読み込み順に関係なく、
同じ配置になること。


==================================================
14. Landmarks
==================================================

以下のような重要物は
Prop Generatorへ任せないでください。

- 灯台
- 空港管制塔
- 大型橋
- 大型ジャンプ台
- 町の中心施設
- 観測所
- 港
- 洞窟入口

World Designへ固定保存してください。

snapToTerrain = true

の場合のみ高さをGeneratorから取得してください。


==================================================
15. Asset Catalog
==================================================

Asset Catalogをfirst-class componentとして実装してください。

ただし

Project.assets

と別に同じAssetRecordを複製して
二重のsource of truthにしないでください。

Project.assetsを正規データとして利用し、
Asset Catalogはその上の

- index
- query
- resolution
- metadata

層として実装することを推奨します。


AssetRecordへ必要に応じて以下を追加してください。

catalog:

- slots
- tags
- biomes
- style
- variantGroup
- contentHash
- status


例:

slots:
  - nature.tree.tropical
  - nature.tree.tropical.medium

tags:
  - tree
  - tropical
  - stylized
  - low-poly

biomes:
  - tropical

style:
  stylized-low-poly

16. Asset Resolver
==================================================

次を実装してください。

resolveAssetSlot(slot, context)

context:

- seed
- biome
- position
- style
- variantIndex

Catalog候補からAssetを選択してください。

同じ

worldSeed
slot
stable placement id

なら同じvariantを返してください。


重要:

Asset Resolverは

Asset Factory
外部Provider
Astra

を呼んではいけません。

Catalogに存在しない場合は、

MissingAsset

として明示的に扱ってください。


==================================================
17. Asset Requirement Planner
==================================================

今回はDUMMYです。

AIを呼んではいけません。

ただしinterfaceは本番を想定してください。


例:

interface AssetRequirementPlanner {
  plan(worldDesign: WorldDesign): Promise<AssetRequirementPlan>
}


Dummy実装ではWorld Designを走査し、

使用されているAsset Slotを抽出してください。

さらに静的Policyで

minVariants

を決めてください。

例:

nature.tree.*      5
nature.rock.*      4
building.*         3
landmark.*         1
course.jump_ramp   3


つまりDummyではあるものの、

固定JSONを返すだけではなく、

World Design → Requirement

の経路を実際に通してください。

将来LLM Plannerへ置換できる境界にすること。


==================================================
18. Asset Factory
==================================================

Asset Factoryの責務:

1. Requirementを受ける

2. Asset Catalogを確認

3. 必要variant数を満たしているか確認

4. 不足していればProviderを検索

5. Policyに合うCandidateを選択

6. 取得

7. Asset Processorへ渡す

8. Catalogへ登録


Provider優先順位の初期値:

1. local
2. kenney
3. polyhaven
4. ambientcg
5. kaykit-local
6. dummy-astra


Factoryはdevelopment/build-time toolです。

Runtime dependencyにしないでください。

==================================================
21. ambientCG ZIP
==================================================

現在Providerがzipを返す可能性を考慮してください。

Asset Processor側でzipをGLBとして誤認しないこと。

安全なZIP展開境界を作ってください。

要件:

- path traversal禁止
- 展開サイズ上限
- file count上限
- nested archive禁止
- MIME/拡張子検証

Archive内にGLB / glTFが存在する場合は
通常Pipelineへ渡してください。

PBR texture setしか存在しない場合は、
無理に偽の3Dモデルへ変換しないでください。

Texture Assetとして登録可能なら登録し、
現在のRendererで利用できない場合は
明示的なunsupported stateとして扱ってください。

推測でMaterialを作ってはいけません。

24. Asset Factory Mode
==================================================

最低限以下のmodeを設計してください。

offline

- Catalog
- Local
- Dummy Astra

のみ。


dry-run

- 不足Assetを表示
- download/generationしない

- 許可された外部Providerから取得可能

CIとUnit Testでは

通常test suiteへ入れないこと。


==================================================
25. Asset Catalog Version / Bake
==================================================

World完成時に
Build Manifestを生成できるようにしてください。

例:

WorldBuildManifest

- worldDesignVersion
- worldId
- seed
- generatorVersion
- assetCatalogFingerprint
- requiredAssets
- resolvedSlots


resolvedSlots例:

nature.tree.tropical.medium
    →
asset-tree-003


必要ならruntime fileの
SHA-256等のcontentHashを保存してください。

Bake後は
Asset Catalogへ新しいAssetが追加されても
完成済みWorldの見た目が勝手に変わらないようにしてください。


==================================================
26. Bake / Lock
==================================================

BakeはTerrainそのものを
すべて巨大Meshとして保存する意味ではありません。

固定する対象:

- World Design
- world seed
- generator version
- catalog fingerprint
- Asset Slot resolution
- landmarks
- course data

Terrain / small propsは引き続き
runtime procedural generationで構いません。


==================================================
27. Far World Proxy
==================================================

今回のゲームでは

「海の向こうの島が見える」

ことが重要です。

通常Chunk Streaming範囲外でも
島や大きな山の存在が見えるようにしてください。


初期実装では、

各IslandDefinitionから

low-resolution island proxy mesh

を作れば十分です。


Near:
normal chunks

Mid:
coarse terrain

Far:
island proxy


通常Chunkが近くに読み込まれたら、
proxyと重複して目立たないようにしてください。

現在のStreaming / Worker構造を壊さないこと。


==================================================
28. World Validator
==================================================

World Generatorの後に
Validatorを実装してください。


最低限検査:

- Spawn pointが海中ではない
- Spawn pointが地面の下ではない
- Roadが異常な急勾配ではない
- Runway上にPropが生成されない
- Landmarkが海中へ沈んでいない
- No-Spawn領域にPropがない
- 必須Asset SlotがCatalogで解決可能
- Islandに有効な陸地が存在
- Course checkpointが不正位置でない


結果:

error
warning
info

を分けてください。


自動Repairは最初から複雑にしなくて構いません。

まずValidatorを信頼できるものにしてください。

==================================================

generation contextを送る方式へ整理してください。
