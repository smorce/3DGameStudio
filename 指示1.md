# 実装依頼

あなたは、ブラウザ3Dゲームエンジン、ゲームエディター、物理シミュレーション、
3Dアセットパイプライン、大規模ワールド、ユーザー体験設計に詳しい
シニアゲームエンジニア兼ソフトウェアアーキテクトです。

以下の仕様に基づき、実際に動作するゲームスタジオを実装してください。

設計書だけを書いて終了しないでください。
既存リポジトリがある場合は最初に構造と実装を調査し、既存コードを壊さず拡張してください。
空のリポジトリの場合は必要なプロジェクトを初期化してください。

不明点のうち実装結果を大きく変えないものは合理的に判断して進めてください。
重要な判断はPLANS.mdに残してください。

==================================================
1. プロジェクトの目的
==================================================

パネキットのように、

- 板を付ける
- タイヤを付ける
- モーターを付ける
- すぐ走らせる
- 作り直す

という非常に簡単な工作体験を入口にする。

ただし内部では、本格的なゲーム制作まで拡張できる
「マシン＋ワールド＋コースを作れるゲームスタジオ」とする。

重要なのは、

「簡単な子供向けゲーム」と
「本格ゲームエディター」

を別々に作らないことである。

同じエンジン、
同じプロジェクトデータ、
同じCommandシステムを、

3種類のユーザーインターフェースから操作する。

製品の概念は以下。

Machine / World / Course Studio

├─ つくる
│   └─ 小学生でも使える簡単画面
│
├─ くわしくつくる
│   └─ 慣れたユーザー向け
│
└─ Studio
    └─ 本格的なゲーム制作環境


==================================================
2. 絶対に守る基本原則
==================================================

以下をNon-Negotiable Requirementとする。

1.
Three.jsのScene/Object3Dそのものを保存データにしない。

2.
RapierのRigidBodyやColliderそのものを保存データにしない。

3.
保存用Project Modelをエンジン実装から分離する。

4.
3段階UIはすべて同じProject Modelを操作する。

5.
簡単モードで表現できない詳細設定が存在しても削除しない。

例：

Studioで
motorTorque = 823
friction = 1.16

と変更したあと簡単モードへ戻っても、
簡単モードがその値を勝手に初期値へ戻してはいけない。

6.
すべての編集操作をCommandとして表現する。

UI → Command → Project Model

とする。

7.
Undo / RedoをCommandシステムで実装する。

8.
AIもUIと同じCommandを利用する。

AIがProject Modelを直接書き換えてはいけない。

9.
編集データと実行データを分離する。

Project Model
    ↓ Compile
Runtime World
    ↓
Three.js + Rapier

10.
Playボタンを押したら即座に試せる構造にする。
ユーザーにビルド・デプロイ工程を意識させない。

7. 接続システム
==================================================

パーツにはConnectorを定義する。

接続可能な場所だけハイライトする。

- Mass
- Joint
- 回転軸

- 摩擦
- 入力

Studioではそれらを編集できるようにする。

==================================================
11. 広大なワールド
==================================================

ワールド全体を巨大な1個のMeshとして扱わない。

World Chunk方式を採用する。

World
├─ Chunk (0,0)
├─ Chunk (0,1)
├─ Chunk (1,0)
└─ ...

カメラ周辺をロードし、
離れたChunkをアンロードできるようにする。

以下の拡張を可能な設計にする：

- Level of Detail
- Frustum Culling
- Instance Rendering
- Chunk Streaming
- Asset Streaming
- Origin Rebasing
- Occlusion対策

初期版ですべてを完成させる必要はないが、
後から追加できない設計にしてはいけない。

木、草、岩など同一アセットを大量配置する場合は
Instanced Renderingを利用できる抽象化を用意する。

16. Asset Provider abstraction
==================================================

特定サイトへの依存を避ける。

interface AssetProvider {
  id
  displayName

  search(query, filters)
  getAsset(id)
  getDownloadOptions(id)
  download(id, option)
}

初期Provider：

1. PolyHavenProvider
2. AmbientCGProvider
3. LocalLibraryProvider
4. KenneyPackProvider

==================================================
17. Poly Haven
==================================================

公式APIを利用する。

ライブAPI利用に必要な条件を守る。

- Provider名をUIに明示
- 「Poly Haven」またはPowered by Poly Havenを表示
- 固有User-Agentを付ける
- レートや障害に備えてキャッシュする

API利用条件を混同しない。

==================================================

- Error Boundary
- Provider health

を持つ。

Providerが落ちてもローカルAssetは使用できること。

==================================================
21. Asset Import Pipeline
==================================================

ダウンロードしたデータを直接ゲームで使わない。

必ずImporterを通す。

Source Asset
    ↓
Validate
    ↓
Normalize
    ↓
Optimize
    ↓
Collider generation
    ↓
Thumbnail
    ↓
Runtime GLB
    ↓
Asset Library

Runtime formatは原則GLB。

Importerは元ファイルを保持できること。


==================================================
22. Optimization Pipeline
==================================================

可能な範囲で、

- Mesh optimization
- Texture compression
- Mesh compression
- unused data removal
- material reduction
- texture resize
- LOD metadata

を扱う。

品質を壊す最適化は勝手に行わない。

Original AssetとRuntime Assetを分ける。


==================================================
23. AI Asset Generation（現状はダミー）
==================================================

費用のかかる実AI生成は、当面呼び出さない。

Asset Browserに、

[素材を探す]
[AIで作る]

を用意する。

検索して適切な既存Assetがある場合は、
まず既存Assetを提案する。

見つからない場合に「AIで作る」へ進むが、
実装はダミー生成とする。

ダミーの要件：

- 有料の外部AI API（OpenAI 等）を呼ばない
- 固定またはルールベースの Structured Plan / プレースホルダ Asset を返す
- UI・Job状態・Command適用の流れは本番想定どおり動かす
- 将来の実Provider差し替えを壊さない interface を維持する


==================================================
24. AI Provider（DummyAIProvider）
==================================================

AI Providerを抽象化する。

interface AIProvider {
  createMachinePlan()
  createWorldPlan()
  createCoursePlan()
  createAssetSpec()
  diagnoseMachine()
}

初期実装（必須）：

DummyAIProvider

- ネットワーク経由の有料AI呼び出しを行わない
- 入力テキストやシチュエーションに応じた、
  決め打ち／テンプレートの Plan を返す
- 遅延・失敗状態もシミュレートできるようにする
  （例：短い delay、たまに failed）

将来差し替え予定（実装しない／接続しない）：

OpenAIAstraProvider 等の実Provider

model 例：
gpt-6-astra

実API接続は明示的に許可されるまで禁止。

API Keyや実Responses API呼び出しのコードパスを
初期実装に含めないこと。

OpenAI API Keyをブラウザへ公開しない、という原則は
将来接続時にも維持する。

可能なところはStructured Output相当の型付きPlanを使用する
（ダミーでも同じ型を返す）。


==================================================
25. AIに直接コードを実行させない
==================================================

AI（ダミー含む）が生成した任意PythonやShellを
Studio serverでそのまま実行してはいけない。

AIはまず、

MachinePlan
WorldPlan
CoursePlan
AssetGenerationSpec

などの構造化データを返す。

それをValidationする。

その後、

Command

へ変換する。

例：

User:
「南国の島に洞窟と大きなジャンプ台があるコース」

DummyAIProvider

↓ WorldGenerationPlan

{
  biome: "tropical-island",
  terrain: {...},
  requestedAssets: [...],
  course: {...}
}

↓ Validate

↓ Commands

terrain.generate
asset.search
asset.place
course.create
checkpoint.add

↓ Project Model

ダミーでも上記パイプラインは本番と同じ経路を通すこと。
Planの中身だけがテンプレート／決め打ちでよい。
