==================================================
3. World Physics Chunk Streaming
==================================================

今回の最優先事項です。


--------------------------------------
3.1 目的
--------------------------------------

現在は描画チャンクを破棄しても、
Rapier側にはWorld全体のColliderが残ります。

これを、

Machine周辺だけ

Rendering Chunk
+
Physics Chunk

を保持する構造へ変更してください。


概念：

        Machine

   [P][P][P][P][P]
   [P][P][P][P][P]
   [P][P][M][P][P]
   [P][P][P][P][P]
   [P][P][P][P][P]

P = Physics-loaded Chunk


Machineが移動：

↓

新しいChunkをLoad

↓

遠いChunkをUnload


--------------------------------------
3.2 対象
--------------------------------------

最低限Chunk化するもの：

- Terrain Collider
- World Entity Collider

可能であれば同じ仕組みで、

- Active CourseのRoad Collider
- Active CourseのObstacle Collider

も空間Chunkへ入れてください。

ただし、
Course機能自体を作り直してはいけません。


--------------------------------------
3.3 Terrain Collider
--------------------------------------

現在のWorld全体を1個のTrimeshにする実装を廃止する。

Terrain GridをChunk単位へ分割する。

Terrainは基本的に、

Rapier Heightfield

を優先して使用してください。

ただし現在のTerrainデータ構造との相性や
Chunk端の継ぎ目に問題がある場合は、

Chunk単位Trimesh

でも構いません。

重要なのは、

World全体を1 Colliderとして保持しないことです。


--------------------------------------
3.4 Physics Chunk Manager
--------------------------------------

world-systemまたはphysics adapter側へ、

PhysicsChunkManager

または同等の責務を持つ仕組みを追加してください。

例：

PhysicsChunkManager
├─ loadedChunks
├─ update(position)
├─ loadChunk(key)
├─ unloadChunk(key)
└─ dispose()

Rapierそのものをworld-systemに漏らす必要はありません。

World System：

「どのChunkが必要か」

Physics Adapter：

「Rapier Colliderをどう作るか」

という分離を維持してください。


--------------------------------------
3.5 Load / Unload Radius
--------------------------------------

Chunk境界でColliderが頻繁に出入りしないようにする。

単純な1 Radiusだけではなく、

load radius
unload radius

または同等のHysteresisを実装してください。

例：

loadRadius = 2
unloadRadius = 3

具体値は既存WorldサイズとTestを見て調整してください。

Hard Codeする場合でも
一箇所の設定値へまとめること。


--------------------------------------
3.6 Update位置
--------------------------------------

PLAY中は、

操作対象MachineのWorld Position

を基準にPhysics Chunkを更新する。

Camera位置を基準にしない。

Cameraだけ遠くへ飛んでも
不要なPhysics Colliderを作らないこと。


--------------------------------------
3.7 Collider Pop対策
--------------------------------------

MachineがChunk境界を越えた瞬間に
足元Colliderが消えないようにしてください。

新規ChunkをLoadしてから、
不要ChunkをUnloadすること。

現在Chunk
+
隣接Chunk

がPhysics Step前に利用可能な状態を保つこと。


--------------------------------------
3.8 Performance Stats
--------------------------------------

既存Statsへ最低限、

physicsChunksLoaded

を追加する。

可能なら、

terrainChunkColliders
worldEntityColliders

も確認できるようにする。


==================================================
4. Instanced Rendering
==================================================

同一World Assetを大量配置したときの
Draw Call削減を実装してください。


--------------------------------------
4.1 対象
--------------------------------------

最低限：

- tree
- rock
- 同一assetIdを持つ静的World Entity

を対象とする。


--------------------------------------
4.2 Grouping
--------------------------------------

最低限、

chunkId
+
assetId
+
LOD level
+
geometry
+
material

でInstance Batchを作れる構造にする。


同一Assetを500個配置した場合に、

Mesh × 500

として扱わない。


--------------------------------------
4.3 Chunkとの統合
--------------------------------------

World全体で巨大なInstancedMeshを1個作らない。

Chunk Streamingと整合するよう、

Chunk単位のInstance Batch

を基本とする。

ChunkをUnloadすれば、
対応Instance BatchもDisposeできること。


--------------------------------------
4.4 GLTF Asset
--------------------------------------

glTFが複数Mesh / Materialを持つ場合、

1 Entity = 1 cloned GLTF scene

を大量生成する実装を避ける。

Asset Templateを一度だけLoad / Cacheし、

各Primitiveまたは同等の単位から
InstancedMeshを構成する。

AssetがInstancing不可能な場合のみ
通常描画へFallbackする。


--------------------------------------
4.5 Picking
--------------------------------------

InstancedMeshに変更したことで
Studio上のObject選択を壊さないこと。

RaycasterのinstanceIdから、

World Entity ID

へ逆引きできる仕組みを持つこと。


==================================================
5. LOD
==================================================

Level of Detailを実装してください。

これをLODと呼びます。

遠くのObjectほど簡単な形状に切り替えて
描画負荷を減らします。


--------------------------------------
5.1 AssetRecord
--------------------------------------

現在の、

runtimeInfo.lodLevels

を実際に意味のある情報へ拡張する。

必要であれば、

runtimeInfo.lods

のような構造へ変更してよい。

例：

lods: [
  {
    level: 0,
    file: "...",
    triangles: 42000,
    distance: 0
  },
  {
    level: 1,
    file: "...",
    triangles: 16000,
    distance: 60
  },
  {
    level: 2,
    file: "...",
    triangles: 5000,
    distance: 150
  }
]


--------------------------------------
5.2 LOD生成
--------------------------------------

Asset Import時に、

Original Asset

は変更しない。

Runtime Assetについて、

LOD0
LOD1
LOD2

を生成できるようにする。

LOD生成には
現在使用中のglTF Transformを活用する。

Mesh simplificationが適さないAssetについては
LOD0のみでも構わない。

Importを失敗させてはいけない。


--------------------------------------
5.3 Quality
--------------------------------------

LOD0は元の見た目を可能な限り維持する。

LOD1 / LOD2だけGeometryを簡略化する。

LOD生成に失敗した場合は、

LOD0

だけでFallbackする。


--------------------------------------
5.4 Renderer
--------------------------------------

Three.jsのLOD機構、
または同等の独自Batch LOD管理を使用する。

ただし、

EntityごとにTHREE.LODを作って
Instancingの利点を失ってはいけない。


推奨構造：

Chunk
└─ Asset Batch
   └─ LOD
      ├─ LOD0 InstancedMesh / Group
      ├─ LOD1 InstancedMesh / Group
      └─ LOD2 InstancedMesh / Group


LOD切替にはHysteresisを使用し、
境界付近で高速に切り替わるのを避ける。


==================================================
6. Asset Collider改善
==================================================

現在、

runtimeInfo.collider = "box"

のみで、
World Asset ColliderもAABB由来Boxです。

これを改善してください。


--------------------------------------
6.1 Collider Mode
--------------------------------------

最低限、

box
convexHull
trimesh

を扱えるようにする。

Terrainは別に、

heightfield

を使用可能にする。


型例：

type ColliderMode =
  | "box"
  | "convexHull"
  | "trimesh";


--------------------------------------
6.2 基本方針
--------------------------------------

Box：

非常に単純なObject
Fallback


Convex Hull：

通常の岩
小物
一般的なStatic Asset


Trimesh：

道路
ジャンプ台
建物
複雑な静的環境Asset


Heightfield：

Terrain


動的Rigid Bodyへ
Trimeshを安易に使わない。

今回対象となる外部World Assetは基本Staticとする。


--------------------------------------
6.3 Collider Data Pipeline
--------------------------------------

Asset Import Pipelineで
Collider用Geometryを作る。

大量の頂点配列をProject JSONへ直接埋め込まない。

Asset Storage側に、

collider data

を別Fileとして保存できる構造にしてください。


例：

assets/<id>/

original.glb

runtime-lod0.glb
runtime-lod1.glb
runtime-lod2.glb

collider.bin
または
collider.json

thumbnail.svg


AssetRecordには

Collider mode
Collider file
Bounds
必要なMetadata

だけ保存する。


--------------------------------------
6.4 Asset Reuse
--------------------------------------

同じassetIdの岩を1000個置いた場合、

Collider Geometry Sourceを1000回Download / Parseしない。

Asset単位でCollider TemplateをCacheし、

各Entityでは、

position
rotation
scale

だけ適用してColliderを生成する。


--------------------------------------
6.5 Fallback
--------------------------------------

Collider生成失敗時は、

Box Collider

へFallbackする。

外部Assetが1個壊れただけで
World全体のPlayが失敗してはいけない。


==================================================
7. Asset Runtime Optimization
==================================================

現在の、

「高品質を維持するため
圧縮・リサイズ・LOD生成は行わない」

という方針を変更する。


新方針：

「Originalは絶対に保持し、
Runtime版だけ最適化する」


--------------------------------------
7.1 Original / Runtime分離
--------------------------------------

必須：

Original

→変更しない。


Runtime

→ゲーム実行向けに最適化。


現在の設計でも
original.glb / runtime.glb
は分かれているため、

この考え方を維持・拡張する。


--------------------------------------
7.2 Runtime Profile
--------------------------------------

最低限、

quality
balanced
performance

の3 Profileを定義できる基盤を作る。

UIを大規模に作り込む必要はない。

Defaultはbalanced。


例：

quality

- LOD0を高品質維持
- Texture上限高め
- 遠距離LODのみ積極的に簡略化


balanced

- 標準Runtime
- Mesh compression
- Texture最適化
- LOD生成


performance

- より強いLOD
- Texture解像度制限
- 転送量とGPU負荷を優先


具体値は実Assetを使ったTestを見て
合理的に決定する。


--------------------------------------
7.3 Mesh Optimization
--------------------------------------

既存の、

dedup
prune
normals

を維持する。

その上で可能なら、

Meshopt
Simplification

などを追加する。

Three.js側で必要なDecoder設定も行う。

Runtime GLBを生成したが
Three.jsで読めない、

という状態は禁止。


--------------------------------------
7.4 Texture
--------------------------------------

Original Textureは保存する。

Runtime用にはProfileに応じて、

- resize
- compression

を行えるようにする。

KTX2を採用する場合は、
Three.js側のKTX2Loaderまで実装・検証する。

KTX2のToolchain導入が今回の変更を
不安定にする場合は、

まずWebP等の安定したRuntime最適化を採用してよい。

「KTX2を入れるためだけに
大量のScopeを増やす」

ことは禁止。


--------------------------------------
7.5 Non-destructive
--------------------------------------

Importをやり直したい場合、
OriginalからいつでもRuntime Assetを
再生成できること。


==================================================
8. 4MB / 64MB制限の設計変更
==================================================

制限そのものを無くしてはいけません。

Security / Memory SafetyのHard Limitと、

ゲーム実行時のPerformance Budget

を分離してください。


現在のような、

「大きいAssetだからImport不可」

だけの設計から変更する。


--------------------------------------
8.1 Upload
--------------------------------------

現在のBase64 JSON uploadは、
大きなGLBに不向きです。

/api/upload

を、

multipart/form-data

またはBinary Stream

を使う方式へ変更してください。

Base64による33%前後のサイズ増加を避ける。


--------------------------------------
8.2 Configurable Import Safety Limit
--------------------------------------

以下のような設定を導入する。

名称は変更して構わない。

ASSET_MAX_SOURCE_MB
ASSET_MAX_AGGREGATE_MB
ASSET_MAX_TEXTURE_DIMENSION
ASSET_MAX_TRIANGLES
ASSET_STORAGE_BUDGET_MB


Hard-codedされた

4MB
64MB

という製品仕様にしない。

環境変数またはServer configから変更可能にする。


--------------------------------------
8.3 Runtime Budget
--------------------------------------

Storage容量と、
Runtimeで同時にLoadする容量を分離する。


Performance Profileに応じて、

- loaded asset bytes
- estimated texture memory
- triangle count
- draw calls

を監視する。


Asset Libraryに500MB保存されているだけで
拒否してはいけない。

現在SceneにLoadされている量を
別に評価する。


--------------------------------------
8.4 Safety
--------------------------------------

巨大FileによるOOMを防ぐSafety Limitは残す。

Security Checkも維持する。

- MIME / format
- GLB header
- unsafe resource paths
- invalid indices
- invalid numbers
- texture dimensions
- triangle count

を削除してはいけない。
